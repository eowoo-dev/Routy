# 장시간 주행 기록

## 수집과 디스크 보존

`EvaluationController`는 주행 전체의 속도·조향·SDK·환경 목록을 보관하지 않습니다. 각 관측을 JSON으로 인코딩한 뒤 `DiskCaptureQueue`의 크기 제한을 확인하고 IO writer로 전달합니다.

- 관측 한 건은 줄바꿈 포함 64KiB 이하, 대기열은 최대 64건입니다. 대기열의 인코딩 데이터는 최대 4MiB입니다. 이는 전체 Android 프로세스의 힙 사용량이 4MiB라는 뜻은 아닙니다.
- `TripArchive`는 기본 60초 또는 원본 512KiB에서 파일을 교체합니다. 교체 직전 한 관측과 열린 손실 구간을 기록하므로 파일 검증 상한은 768KiB입니다. 센서 시각이 정체된 상태로 크기 상한을 넘으면 정상 완료로 처리하지 않습니다.
- SDK 콜백이 없을 때도 1초 tick으로 저장을 진행하고, 파일 동기화와 구간 완료 시 해시·메타데이터를 기록합니다. 원본이 커져도 구간 수만 메타데이터에 남으며 전체 파일 목록이나 원본 목록을 메모리에 모으지 않습니다.
- 가상 환경 HTTP 수집도 독립 IO coroutine에서 실행해 UI/SDK 작업의 복귀를 기다리지 않습니다. 시계 불확실성·관측 간격 등의 평가 품질 기준은 유지합니다.
- 저장 실패, 과도한 관측 크기, 대기열 포화는 실패를 남깁니다. 종료 시점과 경합해도 실패가 사라지지 않으며 `SAVED`로 표시하거나 일부 표본을 조용히 버리지 않습니다.
- 한 주행의 ID는 유지됩니다. 기어 조건은 D단 시작, R/N단 유지, P단 연속 10초 후 종료이며 자동 기록 해제 시 저장 규칙도 같습니다.

`files/sensor-traces/<sessionId>/`에는 `manifest.json`, `raw-N.ndjson`, `window-N.json`과 완료 후 `evaluation-N.json`, `reports.ndjson`, `summary.json`, `complete.json`이 있습니다. `sensor-traces/<sessionId>.json`과 `latest.json`은 작은 색인입니다. 기존처럼 원본을 모두 담은 대형 JSON 파일을 이중 작성하지 않습니다.

구간별 재생 문서인 `evaluation-N.json`에는 해당 구간과 직전 문맥의 원본도 포함돼 추가 디스크 공간을 사용합니다. 모든 원본을 메모리에 합치지 않는 대신 재현성을 위한 보관 공간을 사용하는 구조입니다.

강제 종료 후에는 앱 시작 시 복구 작업이 원본을 검사하고 평가·전송 준비를 재개합니다. 진행 중 수집을 이전 세션으로 자동 재개하지 않으며 정상 주차 종료와 구분한 `INTERRUPTED` 기록을 생성합니다. 마지막 동기화 이후 꼬리의 전원 장애 복구까지 보장하지 않습니다. 디스크 공간이 부족하면 기존 원본을 삭제하지 않고 실패를 표시합니다.

## 한 구간씩 평가

전체 기록을 메모리에 합치지 않습니다. 기본 규칙의 문맥은 파일 수와 관계없이 최근 최대 10초를 유지합니다. 속도·조향·규칙 관련 SDK 관측은 각각 최대 8,192건으로 제한하고, 과거 HVAC·진단 필드 등은 이 문맥에서 제외합니다. 원본 파일은 그대로 보존합니다. 메트릭은 서로 겹치지 않는 구간에서 집계하며 센서 손실 구간은 파일 경계를 넘어 유지합니다.

환경 평가는 `EnvironmentEvaluation.Stream`이 현재 차로, 변경 시작, 안정화 대상과 시각, 신호 준비 시각, 중간 신호 선택과 해제 시간, 앞차 식별자, 진행 중인 간격·정차 사건을 유지합니다. 파일 경계에서 행동을 종료하지 않으며 완료·실제 관측 단절·주행 종료 시에만 확정합니다. 오래 걸리는 차로 변경도 원본 목록을 누적하지 않고 진행 상태와 근거 수치만 유지합니다. 실제 시간 공백·실행 ID 변경·유효하지 않은 관측은 여전히 상태를 끊습니다.

`TripEventJournal`은 기본 규칙의 겹치는 사건을 종류·시간 중첩·도로/회전 맥락으로 합칩니다. `trip-events.ndjson`은 확정 사건 원장이고, 전송 `reports.ndjson` 각 행의 `integratedEvents`에도 동일한 확정 사건을 보존합니다. `segmentation.eventCounts`와 `environmentEventCounts`는 통합 사건 수입니다. 구간별 `report.events`를 단순 합산해 횟수로 사용하지 않습니다. 중복되는 기본 피드백도 맥락과 시간 중첩을 확인해 요약에서 합칩니다.

화면용 이벤트·문맥·연습 항목·피드백 및 환경 복습 그룹은 최대 32개씩 보관합니다. 환경 복습의 관측 품질은 겹치지 않는 구간의 시간만 합산합니다. 각 구간의 전체 상세는 `reports.ndjson`과 서버 상세 보관본에 남습니다. 원시 센서 데이터는 차량 로컬에 보존하며 서버에는 평가 상세를 전송합니다. `continuityVersion: trip-1`로 기존 구간 요약과 구분합니다.

환경 행동 상태를 이어가는 것과 기본 배치 규칙의 전체 주행 동등성은 다릅니다. 기본 가감속·조향 메트릭은 구간 경계의 표본 쌍이 빠질 수 있고, 위치·지도 기반의 긴 회전은 제한된 문맥으로 보류될 수 있습니다. `WINDOW_BOUNDARY` 및 PARTIAL 안내를 유지하며 이 값들을 전체 주행 배치 계산과 완전히 같다고 주장하지 않습니다. 환경 행동의 진행 중 구간과 과거 품질도 확정 후 모두 소급 재분류하지 않습니다.

`evaluation-N.json`은 해당 문맥을 독립 배치 엔진으로 재생하는 문서입니다. 연속 환경 판단을 포함한 전체 아카이브의 재현은 동일한 원본·`evaluation-context.json`을 `TripArchive.recover(...).evaluate()`로 순서대로 처리합니다. 독립 배치 재생 결과를 연속 환경 보고서와 혼동하지 않습니다.

## 앱 중단 이후 복구

`RoutyApplication`은 네트워크 조건 없이 고유 WorkManager 복구 작업을 예약합니다. 수집과 복구는 세션 ID를 먼저 점유하므로 같은 프로세스의 활성 기록을 복구 작업이 읽거나 닫지 않습니다.

- `CAPTURED`: 원본과 창 메타데이터의 연결·해시를 확인한 뒤 평가 및 outbox 등록을 다시 수행합니다. 평가 입력의 센서 가용성·지도는 `evaluation-context.json`으로 고정합니다.
- `CAPTURING`: 닫힌 창을 검사하고 마지막 파일의 완전한 JSON 행까지만 복구합니다. 원래 꼬리는 `interrupted-tail.bin`에 보존하고 미완성/손상 행 이후는 사용하지 않습니다. 정상 주차를 추정하지 않고 `recovery.status: INTERRUPTED`, 잘린 바이트 수와 한국어 복습 안내를 보관합니다.
- outbox가 이미 존재하면 기존 불변 보고서·상세 해시·전송 진행률을 유지하고 완료 표식만 복구합니다. 엔진 갱신을 이유로 이미 전송 준비된 내용을 바꾸지 않습니다.
- 손상된 닫힌 창이나 복구할 관측이 없는 기록은 전송하지 않습니다. `recovery-error.json`에 사유를 남기고 다른 기록의 복구는 계속합니다. 복구된 기록도 기존의 분할 전송·동일 조각 재전송 경로를 사용합니다.

복구는 앱을 다시 실행한 이후에 수행됩니다. 강제 종료 상태에서 백그라운드 수집을 강제로 살리지 않으며, 재부팅 후에도 과거 monotonic 시각을 현재 시각으로 바꾸거나 종료까지의 미관측 시간을 채우지 않습니다.

## 웹 복습 호환

새 요약은 `environment.review`에 제한된 복습 그룹과 관측 품질을 유지합니다. 이전 요약에 복습이 없으면 상세 조회가 보관본을 작은 조각으로 읽어 최대 32개 복습 그룹을 `reviewPreview`에 제공합니다. 원본 `report`와 저장 해시는 바꾸지 않습니다. 이전 창의 겹치는 복습은 시간·종류·제목으로 합치지만 전 주행의 정확한 사건 횟수라고 표시하지 않습니다. 이전 창의 문맥을 포함한 품질 시간을 단순 합산하지 않습니다.

호환 읽기는 최대 32MiB, 한 행 최대 약 2백만 문자로 제한합니다. 제한·손상이 있으면 미리보기의 `limited`로 구분하며 전체 보관본 내려받기는 유지합니다. 웹은 실제로 복습 그룹에 표시한 환경 피드백만 중복 제거하고, 그룹이 없다는 이유로 환경 피드백을 모두 숨기지 않습니다. 중단 복구·미리보기·관측 부족의 의미를 화면에서 구분합니다.

## 전체 상세 평가의 분할 전송

한 요청을 무제한으로 키우는 방식 대신 전체 상세를 192KiB(196,608바이트) 조각으로 나눕니다. 한 요청의 JSON 크기는 여전히 제한하며 전체 상세 크기가 2MiB를 넘을 수 있습니다.

1. `PUT /api/driving-records/{sessionId}/parts/{index}`: Base64 데이터와 SHA-256. 서버는 순서와 해시를 검사하고 같은 조각의 재전송을 허용합니다. 다른 내용으로 바꾸거나 완료 후 새 조각을 붙일 수 없습니다.
2. 차량은 응답의 번호·해시를 확인하고 다음 조각 번호를 outbox에 원자적으로 저장합니다. 재시작·네트워크 오류 후 마지막 확인 지점부터 전송합니다. 서버 저장 후 응답만 유실되면 같은 조각을 다시 보내 확인합니다.
3. `POST .../{sessionId}/complete`: 작은 주행 요약과 전체 조각 수·바이트 수·SHA-256을 보냅니다. 서버는 모든 조각을 하나씩 읽어 검사하고 하나의 주행 기록을 생성합니다. 누락되거나 손상된 부분 전송은 사용자 기록 목록에 나타나지 않습니다. 동시 완료 요청도 한 건만 생성합니다.
4. `GET .../{sessionId}/archive`: 서버는 상세를 메모리에 합치지 않고 NDJSON으로 스트리밍합니다. 차량 설치 인증을 요구하며, 연결 계정은 `/api/account/driving-records/{sessionId}/archive`로 접근합니다.

서버의 24시간 제약은 API와 DB 양쪽에서 제거했습니다. DB는 `BIGINT`를 사용하고 JSON의 정확한 정수 범위 및 UTC 시작·종료 시각 일치를 검사합니다. 기존 단일 보고서 API·outbox와 설치 인증도 유지합니다. 단일 요약 요청의 2MiB 방어 제한은 그대로이며 전체 상세는 분할 전송 경로를 사용합니다. 원본 재생기의 64MiB 제한도 이제 작은 구간별 파일에 적용됩니다.

로컬 outbox는 전체 상세를 담지 않고 요약과 진행 정보만 보관합니다. 업로드·상태 조회는 기존 기록들의 모든 payload를 한꺼번에 읽지 않고 하나씩 처리합니다. 로컬 원본 보존 기간과 서버의 오래된 미완료 전송 정리는 별도 정책으로, 이 변경에서 임의로 삭제하지 않습니다.

## 자동 검증

```powershell
.\infra\pleos\gradle.ps1 ':app:testDebugUnitTest' ':driving-evaluation:test' ':app:assembleDebug' ':app:lintDebug'
.\infra\pleos\gradle.ps1 ':driving-evaluation:archiveMemoryTest'
python -X utf8 -m unittest discover -s infra/pleos -p 'test_*.py'
docker compose -f compose.dev.yaml exec -T web pnpm --filter @routy/web test:records
.\infra\pleos\test-driving-service.ps1 -SkipBuild -LongSeconds 660
.\infra\pleos\test-driving-service.ps1 -SkipBuild -Recovery
```

단위 테스트는 2시간 고빈도 입력의 크기 제한 저장·끝 구간 평가, 36시간 범위, 손상·중단·쓰기 실패, 대기열 포화/과대 관측과 종료 경합을 확인합니다. 별도 `archiveMemoryTest`는 전체 원본이 96MiB를 초과하는 입력을 96MiB 힙에서 저장·읽기·평가하며 CI에서도 실행합니다. 전송 테스트는 2MiB를 넘는 실제 데이터의 분할·응답 유실 후 재개·순서·해시·취소를 검사합니다. API 통합 테스트는 PostgreSQL에서 동시 완료의 단일 기록, 미완료 비공개, 인증 격리, 36시간 저장, 전체 스트리밍 복원을 확인합니다.

에뮬레이터 테스트는 각 디스크 원본의 해시와 구간 연결을 검증하고, 서버의 전체 상세 스트림을 로컬 전송 파일의 크기·해시와 비교합니다. `disk_trace.py`가 원본을 모으는 것은 테스트 PC에서 SDK 입력을 비교하기 위한 작업이며 Android의 수집·평가 경로에서는 사용하지 않습니다.

기존 30초 SDK 검증도 단계 시작·입력 완료·종료를 에뮬레이터 `/proc/uptime`으로 기록합니다. PC에서 탭을 누른 시각이 실제 수집 시작과 같다고 가정하지 않습니다. 진행 중 주행이 있으면 진단을 시작하지 않고, 완료된 시연의 Activity 작업 상태만 초기화해 주차 진입을 확인합니다. 주행 제한을 해제하지 않습니다.

기본 SDK 검증은 기존 세 가지 6초 전환을 유지합니다. 별도 `--environment` 검증은 18초 유지 입력으로 HTTP 환경 수집·SDK 상관관계·품질 분할을 확인합니다. 조향 입력은 직선 도로 모델의 범위 안에 있도록 별도 왕복 패턴을 쓰고 모델 원점을 초기화합니다. 실제로 제외된 시각 불확실성·관측 공백은 보고서에 그대로 남습니다.

## 확인 결과 (2026-11-14)
