# 사용자 화면과 차량 연결

차량의 기본 진입점은 사용자 홈이며, 기존 평가 엔진 진단 화면은 debug 전용 `DiagnosticsActivity`로 분리했습니다. 개발 도구 버튼과 자동 시나리오 검증은 이 화면을 사용합니다. 사용자 홈에서 연습을 시작하고 주차 후 종료·저장할 수 있습니다. 수집 수명과 주행 제한 연동은 [주행 수집 서비스](driving-service.md)를 참고하세요.

## 연결 흐름

1. 주차한 차량에서 **계정 연결 → 연결 코드 발급**을 선택합니다.
2. 스마트폰으로 QR을 스캔하거나 노트북의 웹에서 8자리 코드를 입력합니다.
3. 이메일 계정으로 로그인한 뒤 차량·계정과 기존 기록 포함 안내를 확인합니다.
4. 연결을 확정하면 차량 앱이 상태를 확인하고 코드를 숨깁니다. 웹에서는 계정에 연결된 차량의 주행 기록과 복습 근거를 볼 수 있습니다.

MVP는 계정 하나와 차량 설치 하나를 연결합니다. 운전자 선택·가족 공유·계정 이전·연결 해제는 포함하지 않습니다. 코드는 5분 동안 한 번 사용할 수 있고 새 코드는 이전 코드를 폐기합니다. 차량 설치 비밀 키는 QR에 포함하지 않습니다.

## 개발 환경

- `docker compose -f compose.dev.yaml up -d web`로 변경된 공개 웹 주소 환경 변수를 적용합니다. 브라우저 주소와 `ROUTY_PUBLIC_WEB_ORIGIN`을 일치시킵니다. 기본 주소는 `http://localhost:3000`입니다.
- 기존 DB에는 `pnpm --filter @routy/web db:deploy`와 `db:generate`를 적용합니다.
- 개발 PC와 에뮬레이터는 기본 설정으로 연결할 수 있습니다. 실제 스마트폰에서 localhost QR은 사용할 수 없습니다. 스마트폰에서 접근 가능한 HTTPS 서버 주소를 `ROUTY_PUBLIC_WEB_ORIGIN`으로 설정하고 차량도 같은 서버를 사용해야 합니다.
- 현재 인증은 같은 출처의 웹 브라우저 쿠키를 사용합니다. Capacitor 정적 빌드 분리는 유지하지만 네이티브 앱의 다른 출처 인증 연결은 후속 구현입니다.
- 비밀번호 재설정·이메일 인증·운영 계정 관리 화면은 아직 없습니다.

## 디자인

웹과 차량은 `packages/contracts/design/routy.tokens.json`의 색상과 SIL 라이선스의 SUIT 글꼴을 함께 사용합니다. 짙은 녹색, 밝은 바탕, 도로 모티프를 공통으로 사용하고 차량에는 큰 조작 영역을, 스마트폰에는 하단 메뉴를 적용했습니다. 기록이 없을 때 임의 점수나 샘플 기록을 표시하지 않습니다.

## 검증

- 계정·연결 API 5개: 로그인/로그아웃, 다른 출처 요청 차단, 만료·재발급, 동시 연결, 계정별 기록 격리.
- 기존 주행 기록 API 10개 회귀 검증.
- 차량 앱 단위 검증에 QR 인코딩 후 스캔 결과 일치 검사 포함.
- 에뮬레이터 코드 발급 → 웹의 차량 확인 → 연결 확정 → 차량 연결 완료 및 기존 기록 조회 확인.
- 웹 320·390·768·1440 너비에서 화면 확인. API 테스트용 계정과 화면 검증 연결은 검증 후 정리하며 기존 차량 기록은 유지합니다.

최종 검증에서 웹 서버 빌드와 Capacitor 정적 빌드, 차량 앱 APK 생성·단위 검증 7개·Android Lint를 확인합니다. 기존 에뮬레이터 자동화의 진단 화면 진입점 변경은 관련 Python 검증 14개로 확인했습니다. 차량 가변 글꼴 굵기 수정은 컴파일 검증을 통과했습니다. 후속 화면 검증에서 Windows Pleos 에뮬레이터의 사용자 홈과 계정 연결 화면에 제목·본문·버튼의 굵기가 구분되어 적용되고, 글자 잘림이나 겹침이 없는 것을 확인했습니다. 서버 재시작 후 남아 있던 연결 오류는 다시 확인 버튼으로 해소됐습니다.
